# 服务端设计

版本：v0.4 草案 · [返回总览](00-overview.md)

服务端采用 UE 权威对局服务器，负责比赛规则、射击与伤害、重生、关键破坏和状态复制。它是运行同一工程中服务端逻辑的独立进程；首版不另外建设账号、匹配、排行榜或数据库服务。

## 1. 部署与版本

已确认基线为 4～8 人局域网 Dedicated Server，客户端通过固定 IP 和端口连接。服务器不运行本地玩家、HUD、音频和视觉碎屑生成逻辑。开发机可以同时运行服务器与客户端进行功能验证，但性能验收应分机运行，或明确标注共机资源争用。

当前工程已有 Game、Editor 和新增的 Server Target；服务端默认地图指向现有第一人称地图，并提供本地打包脚本。当前安装版 UE 未登记 Server 构建支持，仍需用同版本源码版引擎验证完整服务端构建。Listen Server 仅用于早期联调，交付与性能验收使用已确认的 Dedicated Server 方案。

所有进程固定引擎补丁版本、游戏构建、地图与 Geometry Collection 资产版本。预破碎层级和碎块索引不能跨不同资产版本混用。首版使用同一发布包并检查构建标识，不设计跨版本兼容协议。

### C++／Lua 分工

首版在 UE Dedicated Server 进程内嵌入 UnLua 执行玩法规则。服务端 Lua 与服务端 C++ 同属权威执行端；客户端 Lua 只能发送操作请求，不能决定服务器结果。C++ 提供网络接口、原生状态与计算能力，Lua 负责易调整的玩法决策和流程。

| 事项 | C++ 职责 | 服务端 Lua 职责 |
| --- | --- | --- |
| 网络与请求入口 | RPC／属性声明、连接与所有权约束、参数范围校验、轮次／生命期校验、请求去重与限流 | 接收有效请求上下文，执行玩法资格判断 |
| 对局 | 提供 GameMode／GameState 原生类、服务器时钟、状态提交和地图操作接口 | 分队、开始条件、阶段流转、胜负、结算及下一局流程 |
| 战斗 | 射线／范围查询、原生计时、复制状态存储、统一提交弹药／生命变化 | 开火／换弹／投掷条件、伤害计算、友伤与保护规则、击杀归属及计分 |
| 重生 | 销毁／生成角色、分配 LifeId、提交初始状态 | 重生时机、出生点选择规则、初始装备与保护规则 |
| 破坏 | 范围筛选、Chaos 应变与求解、断裂队列、关键块复制 | 判断是否允许破坏、选择损伤参数、响应结构事件触发玩法流程 |

需要复制的生命、弹药、得分和比赛阶段由 C++ 声明的属性保存；Lua 决定变更内容，并通过带服务端权限检查的原生接口提交。普通 Lua table 用于服务器内部上下文，不自动复制，也不再维护一份独立的权威生命／比分。RPC 的声明与接收入口保留在 C++，再调用 Lua 规则；调用客户端 Lua 函数本身不会在服务器执行。

规则优先采用“读取上下文 → 返回决策 → 原生检查并提交”的调用方式，避免一次规则尚未计算完就逐项修改权威状态。规则异常时拒绝本次操作并记录上下文；对局阶段等关键流程异常应明确中止或重置对局，不在残缺状态上继续推进。原生提交接口保证权限、数值范围及同一事件不重复生效，不重复实现整套玩法规则。

客户端／服务端／共享脚本的组织见[客户端设计](02-client.md)。服务器只加载服务端及所需共享模块，不执行 UI／表现脚本。发布时固定插件提交、Lua 版本与脚本构建标识，验证 Dedicated Server 的构建、启动、规则执行和脚本打包；当前尚未完成 UE5.8.3 接入验证。

## 2. 状态归属

| 系统 | UE 对应职责 | 维护内容 |
| --- | --- | --- |
| 对局规则 | GameMode，仅服务器 | 加入条件、分队、开始／结束、重生与地图重置 |
| 对局公共状态 | GameState | RoundId、比赛阶段、两队得分、阶段结束时间 |
| 玩家公共状态 | PlayerState | 队伍、击杀、死亡、玩家显示信息 |
| 角色与战斗 | Character、生命／武器组件 | LifeId、生命、存活、保护、弹药、换弹与攻击校验 |
| 破坏管理 | 场景中的破坏管理对象与构件组件 | 破坏注册、应变输入、任务调度、关键状态和统计 |

RoundId 标识当前一局；LifeId 标识同一玩家本次出生。角色销毁／重生和地图重置后，不再接受属于旧轮次或旧生命期的攻击请求。具体承载类与命名在实现时确定，保持职责不变。

## 3. 比赛生命周期

1. 等待阶段接纳未满员、版本一致的连接并自动分队。
2. 满足[玩法文档](01-gameplay.md)的开始条件后进入倒计时；条件失效则退回等待。
3. 对局开始后关闭新加入入口，生成／启用玩家角色，启动权威计时。
4. 服务器结算击杀与比分；分数、时间或队伍离开条件满足后结束。
5. 结算期间禁止新攻击，展示结果；随后重新加载比赛地图，建立新的 RoundId 并清空破坏状态。

重新加载用于可靠恢复首版地图，不实现任意 Geometry Collection 的跨局局部复原。断线玩家移出对局；不实现中途加入与自动重连恢复。其余玩家继续遵循比赛规则。

以上流程由服务端 Lua 编排，通过 C++ GameMode／GameState 接口执行并保存公共状态。计时基于服务器截止时间和原生计时通知，不要求 Lua 每帧轮询所有玩家。

## 4. 操作请求与同步

首版采用普通 Actor 属性复制、RepNotify 与 RPC。项目必须显式配置需要复制的 Actor、组件和属性，不能因启用联网就假定所有玩法自动同步。

| 内容 | 建议方式 | 说明 |
| --- | --- | --- |
| 角色移动 | CharacterMovement 原生路径 | 复用预测、校正和平滑 |
| 单次步枪开火 | 拥有者角色的 Server RPC，不可靠 | RoundId、LifeId、ShotId、瞄准信息；限制频率并去重 |
| 换弹、投掷请求 | 低频可靠 Server RPC | 检查状态、库存与冷却；重复请求不得重复扣减 |
| 生命、弹药、得分、保护、阶段 | 属性复制，必要时 RepNotify | 表达当前状态；不要求每个中间数值都作为事件送达 |
| 手雷 | 服务器生成的复制 Actor | 服务器推进引信、运动与爆炸 |
| 开火、普通命中／爆炸效果 | 有范围限制的短暂事件，可不可靠 | 允许丢失少量表现，不作为伤害或结构真值 |
| 关键结构与关键块 | 原生 Geometry Collection 复制及必要的构件元数据 | 详见破坏文档；不能仅广播爆炸位置和随机种子 |

低频可靠 RPC 不用于逐碎块、逐帧的运动上传。客户端只能通过自己拥有的对象提交操作，不直接对无所有权的场景构件调用 Server RPC。服务器接收攻击后，自行查询受影响对象。

步枪本地预测效果可因不可靠请求丢失而未形成权威射击，客户端以复制状态纠正；不为追求效果必达而积压高频可靠消息。命中提示属于反馈，比分和生命属性才是结果依据。

## 5. 战斗校验

服务器逐次检查：当前比赛允许攻击、请求属于当前 RoundId／LifeId、角色存活、武器可用、未在换弹、弹药足够、射速合法、ShotId 未处理，以及瞄准信息有限且合理。

实现顺序为：C++ 检查请求归属、编号、参数和限流 → Lua 根据当前权威状态判断是否允许攻击 → C++ 执行命中查询 → Lua 计算伤害、击杀与计分决策 → C++ 检查并提交结果，再由 UE 复制。输入限流与武器射速规则分别负责请求预算和玩法条件，不互相替代。

射击起点由服务器角色／视点数据构造或限制在合理范围，不能直接信任客户端任意坐标。服务器完成射线查询，按玩法规则过滤友军与保护状态，再统一扣血和结算。客户端时间仅作诊断或受限输入，首版不做历史命中回溯。

爆炸先查询生效时刻的遮挡与角色伤害，再将本次结构损伤提交给破坏系统，顺序见玩法文档。对已死亡角色重复命中不能重复计分。手雷引信和爆炸只由服务器触发一次。

这些规则是基本权威校验，不宣称提供正式反作弊。若后续引入命中回溯，需要同时设计玩家历史状态与破坏掩体历史，不能只回溯玩家而忽略墙体变化。

## 6. 破坏同步边界

服务器持有关键结构的断裂与碰撞真值；对影响通行和射击的大块运动进行必要同步。客户端独立生成的小碎屑不得阻挡武器查询或影响权威刚体。

首版小地图将关键破坏对象保持为网络相关，暂不引入破坏对象的流式载入和复杂距离裁剪。这样减少“离开相关范围后重新恢复破坏状态”的实现范围，但仍需测量总流量。后续增加中途加入或裁剪前，必须实现并验证快照恢复。

原生 Geometry Collection 复制需要在目标版本与打包构建中验证，包括粗层断裂、关键块位置校正、可靠的最终碰撞结果；不能仅凭编辑器内视觉相似判定正确。若关键块无法达到要求，先降低数量或取消其玩家交互。

## 7. 频率与运行预算

对局更新先以 30 Hz 为测试起点，角色移动、物理步长和对象更新频率分别记录。比赛计时采用服务器时间，不能依赖固定 Tick 次数来累加。服务器不得执行仅客户端需要的扬尘、碎屑音效或逐顶点表现逻辑。

优先降低无关对象和高频状态的复制量，再判断是否需要 Replication Graph 或 Iris。断裂调度预算不等于网络预算；即使分批断裂，也应分别测量每次事件和每客户端的发送量。

同时测量 Lua 规则耗时、跨语言调用次数、临时分配及垃圾回收。少量按次触发的战斗逻辑可以保留在 Lua；逐碎块遍历、物理子步、密集空间查询和复制打包保留在 C++，向脚本返回有界的结果或汇总事件。

## 8. 验证与日志

最小验证配置：一个独立服务器、两个独立客户端；多人验收按总览中的人数基线扩展。网络测试同时检查延迟、抖动和丢包，不只测试本机 PIE。

记录 RoundId、玩家／LifeId、ShotId、拒绝原因、伤害与计分事件、破坏构件标识／版本及关键性能统计。性能测试中避免为每个碎块每帧输出日志，以免日志本身改变结果。

验收需证明：非法或重复请求不重复伤害；客户端不能自行加分；旧生命期请求无效；破坏后至少两客户端的通行与射击查询结果一致；对局结束和地图重置后无旧破坏事件残留。

新增脚本验收：服务端 Lua 的计分／重生决策能在独立客户端观察到；客户端同名函数不能修改服务器状态；规则异常不造成半次扣弹／重复计分；切局后服务端计时器、委托与脚本上下文正确清理。

GitHub Actions 的 PR 检查运行在云端，不依赖本地电脑在线，也不执行 UE 编译或打包。完整构建、联机验证与产物交付在本地执行，入口和启用步骤见[构建与检查说明](../../Build/CI/README.md)。
